# ADR-0004: プレビューは DB に書かずに作る

- 状態: 採用
- 日付: 2026-08-12

## 背景

依頼書47章は `import_sessions` / `import_rows` を持つことを求めている。
一方で39章は「プレビュー前にDBを書き換えない」と定めている。

素直に読むと矛盾しているように見える。
解析結果を `import_rows` に貯めるなら、それも「DBを書き換える」ことになる。

## 判断

**「書き換えない」の対象は本体テーブル（`profiles` / `team_members` など）である**
と解釈する。その上で、**プレビューの段階では `import_rows` にも書かない**。

| 段階             | 本体テーブル | import_* テーブル |
| ---------------- | ------------ | ----------------- |
| 解析・プレビュー | 書かない     | **書かない**      |
| 取り込み実行     | 書く         | 書く              |

### 流れ

```
1. 貼り付け → Server Action が解析 → 結果を返すだけ（DB に触れない）
2. 列マッピングを直す → 再解析 → また結果を返すだけ
3. 「取り込む」→ ここで初めて import_sessions を作り、本体へ書き、
   import_record_links に記録する
```

## なぜプレビューで import_rows にも書かないか

1. **列マッピングを直すたびに解析し直す**。
   途中経過を貯めると、直すたびに古い行を消して入れ直すことになる。
   `import_sessions` が「試しただけ」の行で溢れる。

2. **やめたときに掃除が要る**。
   貼り付けてプレビューを見て「やっぱりやめる」は普通に起きる。
   そのたびにゴミが残るのは、後から履歴を読む人にとって邪魔になる。

3. **解析は速い**。10,000行でも純粋な文字列処理なので一瞬で終わる。
   保存して読み直す理由がない。

## 代償

- 「取り込む」を押した時点でもう一度解析する（同じ入力で同じ結果になる）
- プレビューの内容をブラウザが保持するので、
  巨大なデータではブラウザのメモリを使う（10MB / 10,000行の上限内なら問題ない）
- 途中で離脱すると、プレビューの内容は失われる

## import_rows をいつ使うか

現在は取り込み実行時に記録していない（`import_record_links` だけを記録）。
テーブルは用意してある。次の場合に使う。

- 取り込み結果を後から行単位で見返したい場合
- エラー行だけを直して再実行する機能を作る場合
- 取り込みを非同期（バックグラウンド）にする場合

そのときは「解析結果を `import_rows` に保存 → ジョブが読んで処理」という
形になり、この ADR を見直すことになる。

## 変えるとしたら

行数の上限を大きく引き上げる（10万行など）なら、
ブラウザにプレビューを持たせる方式は無理が出る。
その場合は `import_rows` に貯める方式へ切り替える。
