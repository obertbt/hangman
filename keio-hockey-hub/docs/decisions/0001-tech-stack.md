# ADR-0001: 技術構成と、抽象化する範囲

- 状態: 採用
- 日付: 2026-08-12

## 背景

依頼書で技術構成は指定されている（Next.js / Supabase / R2 / YouTube）。
一方で「特定サービスへの過度な依存を避ける」「長期間自分たちで運用できる」
という要求もある。どこまで抽象化するかを決める必要がある。

## 判断

**ストレージと動画配信は抽象化する。Supabase は抽象化しない。**

| 対象                   |   抽象化   | 理由                                                  |
| ---------------------- | :--------: | ----------------------------------------------------- |
| オブジェクトストレージ |    する    | R2 → S3 → ローカル と替わり得る。interface は薄く済む |
| 動画配信               |    する    | YouTube → Cloudflare Stream の可能性がある            |
| Supabase（DB・認証）   | **しない** | 下記                                                  |

## Supabase を抽象化しない理由

1. **RLS はデータベースと不可分**。Repository 層で包むと、
   どのポリシーが効いているのかコードから見えなくなる。
   RLS はこのシステムの安全性の中心なので、見えなくなるのは危険。

2. **認証もデータベースと結びついている**。`auth.uid()` を前提に
   ポリシーを書いている。ここを差し替えるなら、どのみち全ポリシーを書き直す。

3. **薄い層を作っても意味がない**。`supabase.from('x').select()` を
   `repo.findX()` に置き換えるだけの層は、移植性を上げず、
   読む場所を1つ増やすだけになる。

代わりに、**Supabase を直接触るのは `features/*/queries.ts` と
`features/*/actions.ts` だけ**という規則にしている。
画面から直接触らせない。移植が必要になったら、触る場所はそこに限られている。

## 抽象化しないことの代償

Supabase から移る場合、`queries.ts` / `actions.ts` と
RLS ポリシーの書き直しが必要になる。
これは受け入れる。移る可能性より、
RLS が見える状態を保つことのほうが価値が高いと判断した。

## 純粋なロジックは切り離す

一方で、**業務ロジックは DB から完全に切り離している**。

- `features/import/lib/` — 解析・正規化・照合
- `features/dashboard/lib/` — 今日やることの判定
- `lib/storage/keys.ts`, `lib/storage/validation.ts` — key の組み立て、受け入れ判定
- `lib/auth/permissions.ts` — 権限判定

ここには DB もネットワークも出てこない。単体テストで固めてある。
移植が起きても、この部分はそのまま持っていける。
