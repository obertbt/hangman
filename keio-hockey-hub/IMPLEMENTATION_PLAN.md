# 実装計画

## 1. 要件の理解

### 何を作るのか

慶應義塾大学 女子フィールドホッケー部のためのチームマネジメントシステム。
Notion や Google スプレッドシートに散らばっている運営を1つにまとめる。

ただし**単なる置き換えではない**。既存のツールをそのまま再現するのではなく、
女子フィールドホッケー部の活動に合わせて作り直す。

### 中心にある循環

```
シーズン目標 → 今週のテーマ → 今日の練習 → 練習前の準備 → 練習・試合
  → 日報 → トレーニング記録 → 動画による質問 → コーチのフィードバック
  → 次回の個人課題 → スキル進捗・承認 → 次の練習へ
```

**この循環をつなげることが最大の目的。**
個々の機能が単体で動いても、つながっていなければ意味がない。

具体的には、次の2つが「つながっている」ことの実装になる。

- コーチの回答の `next_task` が、次の練習の `practice_goals` になる
- コーチの回答の `related_skill_id` が、スキル申請につながる

### これは管理システムではない

依頼書の最重要設計思想。
**選手が成長するための行動支援システム**として設計する。

迷ったときの優先順位（依頼書3章）:

1. 選手が「今日何をすればいいか」を迷わない
2. スマートフォンから素早く入力できる
3. 選手が動画を使って気軽に質問できる
4. コーチが未対応の依頼を見落とさない
5. フィードバックが次の練習課題につながる
6. 過去から現在までの成長を確認できる
7. 入力負担を増やしすぎない
8. 個人情報・非公開情報を守る
9. 動画による容量増大を抑える
10. 特定サービスへの過度な依存を避ける
11. 長期間自分たちで運用できる
12. 過去の Google スプレッドシート資産を失わない

この順位が、実装の判断に実際に効いている例:

- 「今日」の画面は情報一覧ではなく**残っていること**を最初に出す（1）
- タップ領域44px、入力欄16px、下部ナビゲーション（2）
- 60秒制限は技術的制約ではなく、質問を絞らせる設計（3・9）
- 仮想クリップで動画を切り出さない（9）
- 移行は既定で上書きしない、取り消せる（12）

## 2. MVP の範囲

### 最初の到達点（依頼書66章）

```
管理者: ログイン → Google Sheets からコピペで選手登録
        → シーズン作成 → 今週のテーマ作成 → 練習予定作成
選手:   ログイン → 今日のダッシュボード → 今週のテーマ → 今日の練習予定
```

**これが動くまで次に進まない。** ここは Phase 3 で到達した。

### MVP に含めないもの（依頼書76章）

AI 分析 / 自動選手追跡 / 動画への描画 / 自動ハイライト / 自動字幕 /
FFmpeg 同期処理 / Cloudflare Stream / Google Sheets リアルタイム同期 /
LINE / Discord / Strava / Google Fit / ネイティブアプリ /
リアルタイムチャット / Notion クローン / 自由ブロックエディタ

ただし将来足せる形にしておく（`ObjectStorage` / `VideoProvider` の抽象化）。

## 3. アーキテクチャ

[docs/architecture.md](docs/architecture.md) を参照。要点だけ:

- Next.js App Router。Server Components が基本、必要な所だけ Client
- 業務ロジックを画面に書かない。`features/*/lib/` に純粋な関数として置く
- Supabase は抽象化しない。ストレージと動画配信は抽象化する（[ADR-0001](docs/decisions/0001-tech-stack.md)）
- 権限はアプリ側と RLS の両方で守る

## 4. データベース

[docs/database.md](docs/database.md) を参照。要点だけ:

- `seasons` → `weeks` → `events` が背骨。ここは後から変えにくい
- `profiles` は `auth.users` と分離（[ADR-0002](docs/decisions/0002-profile-identity.md)）
- ほぼ全テーブルに `team_id` を持たせる（RLS を単純に保つため）
- 状態の種類は enum ではなく `text` + CHECK
- 重要な状態変更はトリガで履歴を残す

## 5. 権限

[docs/permissions.md](docs/permissions.md) を参照。要点だけ:

- role は既定値。`member_permissions` が上書きする
- 判定は SQL と TypeScript の2か所。**変えるときは必ず両方**
- `import.execute` はコーチにも既定では渡さない

## 6. RLS

[docs/security.md](docs/security.md) を参照。要点だけ:

- 全テーブルで有効。`anon` は public のデータに一切触れない
- 判定は `security definer` 関数に逃がす（再帰を避けるため）
- 保証したいことは `supabase/tests/rls_test.sql` で実際に確認する

## 7. Import アーキテクチャ

[docs/import.md](docs/import.md) を参照。要点だけ:

- プレビューまで DB を書き換えない（[ADR-0004](docs/decisions/0004-preview-before-write.md)）
- 吸収するが推測しない（[ADR-0005](docs/decisions/0005-normalization-policy.md)）
- 既定は上書きしない。取り消せる
- `team_id` は必ずサーバーが入れる（[ADR-0003](docs/decisions/0003-import-write-path.md)）

## 8. Video アーキテクチャ

[docs/video-architecture.md](docs/video-architecture.md) を参照。要点だけ:

- 長時間は YouTube、短編は R2、その間を**仮想クリップ**が埋める
- 仮想クリップは実ファイルを作らない。DB の1行だけ
- 動画本体はアプリサーバーを通さない

## 9. Storage アーキテクチャ

[docs/storage.md](docs/storage.md) を参照。要点だけ:

- Private Bucket、署名付き URL、DB に URL を保存しない
- storage key に氏名を入れない、チームで区切る
- 論理削除30日 → 物理削除

### 依頼書の Phase はここまで

Phase 0 から 9 まで、依頼書79章の並びを実装した。
循環は Phase 8 で閉じ、Phase 9 で「長く自分たちで運用する」ための道具が揃った。

### 残っていること

大きいものから。

1. **招待メールの自動送信**。いまはリンクを作って手で渡す。
   LINE で送れるので実用上は困らないが、人数が増えたら効いてくる
2. **集計と掃除の定期実行**。いまは管理画面から手で押す
3. 出欠、練習メニューの定型化
4. 測定結果の取り込み（Import Center）、測定会の編集と削除
5. 卒業・退部の一括処理（61章）

いずれも「無くても回る」ものにした。
先に作ったのは、無いと循環が止まるものだけ。

### 提出状況を直して分かったこと

- **RLS で書けないことに突き当たったら、要件のほうを疑う**。
  「あることは見せるが、中身は見せない」は RLS では書けない。
  そのため「自分だけ」の日報は提出状況から行ごと消え、
  ちゃんと書いて出した選手が未提出として並んでいた。
  RLS としては正しく動いていたので、穴を探しても見つからない。
  画面の目的（見落としを減らす）から見て初めて、間違いだと分かる
- **機構の都合を利用者に押し付けない**。
  「RLS がそうなっているので未提出に見えます」は、
  選手にもコーチにも通じない。分けるべきものを分ける
- **security definer の関数が返すものが、そのまま境界の定義になる**。
  ビューにしなかったのは、何を返して何を返さないかが
  定義の中に残らないため。関数なら理由をその場に書ける
- **黙ってやらない**。出したことが伝わるなら、選手がそれを知っている必要がある。
  公開範囲を選ぶその場に、そのとき何が伝わるかを出した

### 日報コメントを作って分かったこと

- **同じ間違いを、別のテーブルで繰り返した**。
  Phase 7 で「権限と公開範囲は別のもの」と学んだのに、
  `report_feedbacks` のポリシーはまったく同じ形で壊れていた
  （権限だけを見て、日報の `visibility` を見ていなかった）。
  選手が「自分だけ」にした日報に、コーチがコメントを書けた
- **親のポリシーを写した子のポリシーは、親が変わると置き去りになる**。
  条件を書き写すのをやめ、`app.can_see_report()` にまとめて
  読みと書きの両方から呼ぶ形にした。
  これで、選手が後から公開範囲を狭めれば、
  すでに書かれたコメントも一緒に見えなくなる
- **返事が来ない、が一番こたえる**。
  コメントの有無をコーチの「今日」と提出状況の両方に出し、
  未コメントのものを上に並べた。3章の4（見落とさない）と同じ扱いにした
- 動画を撮って質問するほどではない日の往復を、ここが担う。
  動画の質問（Phase 5〜7）は重い。毎日回るのは、こちらの軽い経路

### 招待を作って分かったこと

- **RLS は「中の人」を守る仕組みなので、入口だけは別に開ける必要がある**。
  招待を受け取る人はまだどのチームにも属していないため、
  どのポリシーにも当てはまらない。`security definer` の関数を
  `anon` にも開けるのは、この1点のためだけ
- **リンクはパスワードと同じ重さで扱う**。
  「持っているだけでアカウントを作れる」ものなので、生の値を DB に残さない。
  残すのは sha256 だけで、再表示もできない。無くしたら作り直す。
  署名付き URL を保存しないのと同じ考え方
- **権限の壁を作ったら、その周りに抜け道が無いか見る**。
  0018 で「役割を変えられるのは管理者だけ」にしたが、
  招待で役割を渡せると、そこが抜け道になる。
  壁を作った後は、同じ結果に届く別の道を探しにいく
- 認証利用者の作成には管理APIが要る。ADR-0003 と同じく、
  service role を使う場所を1か所に閉じ、前後を固めた
  （先に招待の有効性を確かめる → 作る → 結び付ける → 失敗したら作った利用者を消す）
- 期限の検査は**作成時だけ**にする。
  「期限が過去の招待は作れない」は正しいが、それを UPDATE にも掛けると、
  時間が経った招待に `accepted_at` を入れられなくなる

### 復元を作って分かったこと

- **守りを固めたら、その分だけ戻す手立てを用意する**。
  0019 で「消したものは消した人からも見えない」に直した時点で、
  間違えて消したものを取り戻せなくなっていた。
  守り方を変えたら、それで壊れる導線が無いかを見にいく
- **戻すときは、削除に付随して起きたことも取り消す**。
  動画を戻しても物理削除の予約が残っていると、
  30日後に実体だけ消えて「再生できない動画」が残る。
  削除が複数の表を触っているなら、復元も同じ数だけ触る
- **状態の名前に意味を2つ持たせない**。
  `upload_status = 'deleted'` は「R2 から実体が消えた」の意味だったのに、
  `soft_delete_video` が論理削除の時点で立てていた。
  そのせいで**アプリから消した動画が容量の集計から外れていた**。
  実体はまだ R2 にあるのに「もう無いもの」として数えていたことになる
- テストは**実際の経路**で書く。容量のテストは `deleted_at` を手で入れていたので、
  `soft_delete_video` 経由の壊れ方を見逃していた

### 運用の穴を塞いで分かったこと

- **`for all` のポリシーは SELECT にも効く**。
  「見る条件」と「書く条件」を別ポリシーに分けたつもりが、
  許可ポリシーは `or` で足し合わされるため、
  書ける立場の人には論理削除した行が見え続けていた。**17個が同じ形**。
  選手が消した日報が自分の一覧に残る、といった形で表に出る
  （`0019_soft_delete_visibility.sql`、docs/security.md 12章）
- それを直すと、今度は 11章の形（更新後の行が見えなくなる更新は通らない）になる。
  論理削除は `security definer` の関数を通すしかない。
  0013 で動画に対してやったことを、記録とスキル定義にも広げた
- **「スタッフなら書ける」と書いた表に、権限そのものを決める列があった**。
  `team_members.role_code` がそれで、マネージャーが自分を管理者に昇格できた。
  `role_code` はただの列ではなく、権限の壁そのもの
  （`0018_role_guards.sql`、docs/security.md 13章）
- **締め出しの防止も安全のうち**。最後の管理者を降格・退部できると、
  誰も役割を戻せずチームごと操作不能になる。
  「悪意ある操作を止める」だけでなく「戻せなくなる操作を止める」も要る
- 画面が無い機能は、無いのと同じ。スキル定義は SQL でしか作れず、
  Phase 8 を作り終えていたのに使い始められない状態だった（3章の11）

### 測定で分かったこと

- **項目によって良い方向が逆**。50m走は小さいほど良く、YoYoテストは大きいほど良い。
  増減だけを見せると「速くなったのに落ちた」と読めてしまう。
  比較・自己ベスト・折れ線の上下、すべてを `better` で切り替えている
- **折れ線1本にライブラリは要らない**。Recharts を入れる予定だったが、
  SVG の `path` を組み立てるだけで足りた。依存を増やさない（3章の10）ぶん、
  組み立てを純粋関数にできて、テストで固められた
- 記録会では30人ぶんを次々に入れる。1件ごとに保存ボタンを押させると手が止まるので、
  入力欄から離れた時点で保存する。ただし「押していないのに保存された」が不安なので、
  保存中と保存済みを小さく出す（3章の7）
- **空欄と 0 は違う**。「測っていない」と「0だった」を同じ扱いにしない。
  空欄で送られたら記録を消し、0 は記録として残す

### Phase 9 で分かったこと

- **RLS のポリシー漏れは、また同じ形で出た**。
  `storage_usage_snapshots` も select しか無く、集計を書き込めなかった。
  Phase 8 の `notifications` と同じ形。
  新しい表を足したら「使う操作のぶんだけポリシーを書く」を
  チェック項目にしたのは正しかったが、既にある表の見落としは残っていた
- **`psql | grep` の終了コードは grep のもの**。
  DB テストが ERROR で落ちても「すべて通りました」と出ていた。
  テストが失敗を報告しないのは、テストが無いより悪い
- **CSV は書けるだけでは足りない**。
  Excel は BOM が無いと日本語を崩し、`=1+1` を数式として実行する
  （CSV インジェクション）。書き出しは「相手のアプリがどう解釈するか」まで含めて設計する
- 書き出したものを取り込みに通し直すテストを書いた。
  引用符・改行・区切りが入ったデータで往復できることを、
  Phase 2 の parser と繋いで確かめている
- **「誰が何を出せるか」を書き出し側で決め直さない**。
  RLS が見せてくれたものをそのまま出す。
  権限判定を2か所に置くと、必ずどちらかが古くなる

### Phase 8 で分かったこと

- **RLS のポリシーを書き忘れた表は、黙って動かなくなる**。
  `notifications` と `notification_targets` は RLS を有効にしてあるのに
  INSERT のポリシーが1つも無く、Phase 6 以降の通知は**1件も作られていなかった**。
  気付けなかったのは、アプリ側が通知の失敗を握りつぶしていたため。
  supabase-js は例外を投げず `{ error }` を返すので、try/catch では拾えない
  （`0015_notification_insert.sql`）
- **失敗を握りつぶすなら、せめてログに残す**。
  「落ちても本筋は止めない」は正しいが、「何も言わない」は違う。
  通知の失敗は `console.warn` に出すようにした
- **ポリシーの中から他の表を select すると、その表の SELECT ポリシーも効く**。
  「自分が作った通知か」を素朴に書いたら、宛先を入れる前の通知は自分にも見えず、
  いつまでも条件を満たせなかった。判定は `security definer` の関数に逃がす
  （0002 の `app.*` と同じ理由）
- **「自分で自分を承認できる」は、RLS を素直に書くと簡単に生まれる**。
  `player_skills` の更新ポリシーが `本人 or 審査担当` だったため、
  選手が自分の到達状況を `approved` にできた。スキル承認はこのシステムで唯一
  「他人に認めてもらう」記録なので、自分で書けるなら意味がない（`0014_skill_guards.sql`）
- **DB テストは、失敗しても失敗と言わないことがある**。
  `psql | grep` の終了コードは grep のものになるため、
  SQL が ERROR で落ちても「すべて通りました」と出ていた。
  出力を見て自分で判定するようにした（`scripts/run-db-tests.sh`）
- 同じトランザクションの中では `now()` が進まない。
  履歴の「最後の1件」を `created_at` の並び順で取ろうとすると当てにならない。
  「どこからどこへ動いたか」で確かめる

### Phase 7 で分かったこと

- **`visibility` を RLS の条件に入れ忘れると、公開範囲は飾りになる**。
  `videos_select` が `video.view_team`（全選手が既定で持つ権限）を
  単独の枝に書いていたため、`private_staff` の動画がチーム全員から見えていた。
  権限（見てよい人か）と公開範囲（誰に向けた動画か）は別のもので、
  掛け合わせないと意味がない（`0012_video_visibility_fix.sql`、docs/security.md 9章）
- **PostgreSQL は UPDATE のとき、更新後の行にも SELECT ポリシーを適用する**。
  閲覧ポリシーが `deleted_at is null` を条件にしている以上、
  `update ... set deleted_at = now()` は必ず弾かれる。
  ポリシーの書き方の問題ではなく、論理削除とこの規則は両立しない。
  削除は `security definer` の関数を通すことにした（`0013_soft_delete_rpc.sql`）
- 進み具合の表示に `fetch` は使えない（送信中の割合が取れない）。
  XHR の `upload.onprogress` を使う。回線の細い場所で数十MBを送ると
  1分近くかかるので、割合が出ないと「固まった」と思われて中断される
- 署名付き URL は「発行して終わり」ではない。期限が切れた状態で
  再生しようとしたときに取り直せる導線が要る

### Phase 6 で分かったこと

- 状態遷移の表を1か所（`features/feedback/lib/state.ts`）に置き、
  画面のボタンをそこから作る形にした。
  「この状態のときだけこのボタンを出す」を画面に書かないので、
  規則を変えるときに直す場所が1つで済む
- DB のトリガと同じ規則を TypeScript にも持つことになるが、
  役割が違う。DB は「不正な遷移を絶対に通さない」、
  TS は「いま押せるボタンを決める」。両方要る
- 回答の必須項目は「結論」だけにした。28章には10項目あるが、
  全部埋めないと出せない作りだと、忙しいコーチは回答を後回しにする。
  ひとことでも返ってくるほうが選手にとって価値がある

### Phase 5 で分かったこと

- **RLS だけでは参照先のチームを守れない**。
  `video_clips` のポリシーは「作成者が自分」「team_id が自分のチーム」しか
  見ておらず、別チームの動画を指すクリップを作れてしまった。
  チームの一致は権限ではなくデータの整合性なので、トリガで守ることにした
  （`0011_cross_team_reference_guard.sql`、docs/security.md 8章）
- 外部キーを足したら、参照先のチーム一致を必ず確かめること
- 仮想クリップの切り替えは `iframe` の `key` を変えて作り直す。
  `src` だけ変えても再生位置が戻らない

### Phase 4 で分かったこと

- 段階評価（1〜5）は画面のあちこちで使うので、部品にまとめた（`RatingField`）。
  タップ領域44px以上、両端に意味を書く、という決まりを1か所で守れる
- 「実施時間」「ペース」は人に計算させない。入力の負担が減るほど記録が続く
- `event_id` が null になり得る列では、unique 制約による upsert が使えない
  （Postgres では NULL 同士を重複とみなさないため）。
  「探して、あれば更新、無ければ作成」の形にしている

## 11. 技術的なリスク

| リスク                        | 影響                       | 対策                                                                   |
| ----------------------------- | -------------------------- | ---------------------------------------------------------------------- |
| RLS の書き漏れ                | 情報漏洩                   | `rls_test.sql` で実際に確認。テーブル追加時の手順を security.md に記載 |
| 権限判定が SQL と TS でずれる | 権限の穴                   | 両方に「変更時は両方直す」と明記。既定権限の表を3か所で一致させる      |
| 移行での二重登録・上書き事故  | 過去データの破損           | 既定は insert_only、取り消し可能、照合を厚くテスト                     |
| 移行での推測ミス              | 誤ったデータが正しく見える | 推測しない方針（ADR-0005）。曖昧なら人に返す                           |
| 動画で容量が膨らむ            | 費用超過・運用停止         | 仮想クリップ、60秒/50MB、1日5本、日次集計                              |
| Supabase への依存             | 移行困難                   | 触る場所を queries/actions に限定。業務ロジックは DB 非依存            |
| Next.js の大きな変更          | 保守困難                   | バージョンを固定。`node_modules/next/dist/docs/` を参照する運用        |
| 引き継ぎの断絶                | 数年で使われなくなる       | docs 一式、部のアカウントで運用、復元手順を試す                        |
| 型定義の手書き                | DB とのずれ                | Supabase を用意でき次第 `pnpm db:types` に切り替える                   |

## 12. 前提（確認できていないこと）

依頼書に書かれておらず、こちらで決めたこと。
**実際の運用と食い違う場合は指摘してください。**

1. **チームは1つ**。データ構造は複数チームに耐えるが、
   画面は「自分が所属する最初のチーム」を見る作りになっている
2. **週は月曜始まり**を想定。ただし開始日・終了日を手で指定するので、
   日曜始まりでも運用できる
3. **学年は1〜6**。大学院生や留年を考慮して6まで許容している
4. **背番号は在籍中のみ重複禁止**。卒業生と同じ番号は使える
5. **卒業生のログインは止める**が、記録は残す。
   卒業後に本人が過去の記録を見たい場合の扱いは決めていない
6. **メールアドレスは任意**。持っていない選手も登録できる。
   その場合、後からアカウントを配るときに手作業で結び付ける
7. **動画の長さは登録時に人が入力する**。YouTube API を呼ばない
8. **通知はアプリ内のみ**。メール・LINE 等への配信はしない
9. **監査ログは5年**。自動削除の仕組みはまだ無い（Phase 9）
10. **タイムゾーンは Asia/Tokyo 固定**。海外遠征時の扱いは考えていない
